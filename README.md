# «Сетевой анализ»: перехват HTTP-трафика и исследование XSS (Scapy + Google Gruyere)

В работе выполняются четыре этапа: настройка окружения Scapy, перехват и
разбор HTTP-трафика учебной площадки Google Gruyere, эксплуатация XSS-
уязвимостей на этой площадке и анализ сохранённого pcap-файла на следы атаки.

| Файл | Назначение |
|---|---|
| `capture.py` | Сниффер HTTP-трафика: перехват через Scapy, распаковка gzip/deflate, сохранение в `.pcap` |
| `analyze.py` | Анализ pcap: поиск XSS-полезных нагрузок в запросах и ответах, сводка по трафику |
| `exploit.py` | Автоматизация отправки XSS-полезных нагрузок в Gruyere |
| `Башкиров Евгений Романович.pcap` | Перехваченный трафик: обычная сессия + эксплуатация XSS |
| `requirements.txt` | Зависимости проекта |

- ОС: Windows 11 + WSL2 (Ubuntu)
- Python 3.x, Scapy 2.x
- Виртуальное окружение `~/scapy-env` (создано из-за PEP 668 — системный

Ход работы

# Этап 1. Настройка Scapy

1. Установлен Scapy в виртуальное окружение, проверена возможность перехвата с правами root:

```bash
sudo ~/scapy-env/bin/python -c "from scapy.all import sniff; sniff(count=3, timeout=10)"
```

2. Ядро Linux при перехвате чужого TCP-потока отправляет RST-пакеты и
   обрывает соединение. Для корректного захвата правило добавлено до
   работы и удалено после:

```bash
sudo iptables -A OUTPUT -p tcp --tcp-flags RST RST -j DROP
# ... работа ...
sudo iptables -D OUTPUT -p tcp --tcp-flags RST RST -j DROP
```

# Этап 2. Перехват и анализ трафика

1. Запущен перехват: `sudo ~/scapy-env/bin/python capture.py <файл>.pcap`
2. Выполнена сессия на Gruyere без атак: регистрация (Sign up), вход,
   навигация по страницам, создание обычных сниппетов, заполнение профиля.
3. Скрипт печатает в терминал разобранные пакеты:

   - метод запроса (GET/POST), путь и параметры URL;
   - все HTTP-заголовки;
   - тело запроса и тело ответа.

4. Тело HTTP-ответа сжато сервером (gzip), в `capture.py` добавлена
   функция `decode_body()`, которая по заголовку `Content-Encoding`
   распаковывает `gzip` и `deflate` перед выводом и анализом.

# Этап 3. Рекон-анализ и эксплуатация XSS

Точки входа, найденные при рекон-анализе (по документации Gruyere):

1. **Поле сниппетов (New Snippet)** — stored XSS: введённый HTML
   сохраняется и исполняется при просмотре любым пользователем.
2. **Путь URL** — reflected XSS: часть пути после идентификатора
   инстанса отражается в ответе без экранирования.
3. **Поле цвета в профиле** — attribute injection: значение попадает
   в атрибут HTML-тега, кавычки позволяют дописать обработчики событий.

Использованные полезные нагрузки:

```
<a onmouseover="alert(1)" href="#">read this!</a>
<img src=1 onerror=alert(1)>
<p <script>alert(1)</script>hello
```

```
GET /<script>alert(1)</script>          ← reflected, payload в пути URL
```

```
red' onload='alert(1)' onmouseover='alert(2)   ← цвет профиля
```

Всё взаимодействие велось при включённом сниффере; исполнение payload
(всплывающие `alert`) подтверждено визуально в браузере. Итоговый
трафик сохранён в pcap-файл репозитория.

**HTTP-запрос с XSS-нагрузкой:**

- метод: `POST /newsnippet2` (stored XSS) и `GET` (reflected XSS);
- параметр с нагрузкой: `snippet=<payload>` в теле POST-запроса;
- на уровне HTTP payload выглядит как URL-кодированный HTML:
  `%3Cscript%3Ealert(1)%3C/script%3E` и т. п. — кодировка снимается
  браузером при отображении страницы, поэтому нагрузка исполняется.

**HTTP-ответ сервера:**

- статус 200 OK, payload возвращается в теле ответа без экранирования;
- присутствует в HTML-теле (текст сниппета в списке), в значениях
  атрибутов (`style='...' onload='...'`) и в отражённом пути URL.

**Сравнение с обычным трафиком:**

- коды ответов, заголовки и структура страницы не изменились;
- единственное отличие — содержимое тела: в ответах на атакующие
  запросы появляются нехарактерные теги и обработчики событий
  (`<script>`, `onerror`, `onmouseover`, `onload`), отсутствующие
  в «чистой» сессии.

## Описание изменений в трафике (вывод)

До атаки трафик содержит стандартные запросы: GET страниц Gruyere,
POST формы регистрации и обычных сниппетов с текстовым содержимым.
Во время атаки в трафике появились:

1. POST-запросы к `/newsnippet2`, в теле которых параметр `snippet`
   содержит HTML с обработчиками событий, переданный в URL-кодировке;
2. GET-запросы, в которых payload находится прямо в пути URL;
3. соответствующие ответы сервера (200 OK), в которых полезная
   нагрузка отражается в HTML-теле без фильтрации.

Синтаксис HTTP, статусы и заголовки не отличаются от легитимных
запросов — меняется только содержимое тела ответа. Именно поэтому
XSS «тиха» на транспортном уровне и не обнаруживается средствами
фильтрации пакетов без контентного анализа.

## Выводы

- Scapy позволяет перехватывать и разбирать HTTP-трафик при условии
  запуска с правами root и подавления RST-пакетов ядра.
- Сжатие ответов (gzip) — обязательный фактор при анализе: без
  распаковки тела ответов недоступны для анализа.
- XSS-полезная нагрузка проходит через сервер без фильтрации и
  исполняется в браузере жертвы. Признаки атаки в трафике: payload
  в параметрах запросов и его необработанное отражение в теле ответа.
- Защита от таких атак — экранирование пользовательского ввода
  на стороне сервера и CSP на стороне клиента, а на уровне сети —
  контентный анализ тел HTTP-запросов/ответов.
